# PLANORA PROJECT RULES v2

## Read First

Before coding any Planora module, read:
1. `01_PLANORA_DESIGN_SYSTEM.md`
2. `03_PLANORA_SCREEN_MAP.md`
3. This file
4. The task assigned to you in `05_PLANORA_TEAM_TASKS.md`

## Product Identity

Planora is a modern house-planning and visualization product.

Visual identity:
- warm architectural
- premium but simple
- natural materials
- modern UI
- calm, not flashy

Never turn Planora into a generic blue SaaS dashboard.

## Technology

Use the project's agreed stack.

Preferred direction:
- React
- TypeScript
- Vite
- Tailwind CSS or the team's chosen styling approach

Do not change the framework or introduce another UI framework.

## AI Coding Rules

When using Cursor, Copilot, Claude Code, or another coding AI:

1. Read the Planora documents first.
2. Inspect the current files before creating new ones.
3. Build one section/component at a time.
4. Reuse existing components.
5. Follow the exact color and typography tokens.
6. Do not invent a new visual style.
7. Do not redesign another member's module.
8. Do not install unnecessary packages.
9. Explain major changes before making large architectural changes.
10. Test after each meaningful change.

## Design Rules

Never:
- randomly change colors
- use a different font
- create another button style unnecessarily
- use excessive glassmorphism
- use neon colors
- make every section heavily animated
- use generic AI/robot imagery
- replace the Planora warm architectural identity with a standard blue SaaS design

## Separate Local Work

Some team members are not familiar with Git/GitHub.

They may work in separate local project copies.

This is acceptable for the first development phase.

They MUST:
- use the same design documents
- use the same stack
- keep their work inside their assigned module
- report new dependencies
- provide changed files to the project lead

The project lead will integrate the modules.

## If Something Is Unclear

Do not invent a new requirement.

Ask the project lead or leave the part as a clearly marked integration point.

## Definition of Done

A module is complete when:
- it follows the Planora design system
- it is responsive
- it works without obvious UI errors
- it does not break unrelated areas
- it contains no unnecessary placeholder UI
- the project lead knows about any new dependency
